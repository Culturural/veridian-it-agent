**Immutability:**
Source models (Policy, EmployeeRequest, Ticket) are frozen to prevent accidental modification of ground truth data.

**Ticket Semantics:**
Implemented `TicketContext.from_ticket()` static method to derive active/closed status based on assignment rules, keeping the logic in one place.

- Confidence and relevance scores constrained to 0.0-1.0 using Pydantic validators

### Architectural Principle

Source data, derived agent information, and system-generated information remain separate throughout the application. This separation:
1. Prevents policy invention
2. Maintains data integrity
3. Enables clear traceability
4. Simplifies testing

### Critical Architectural Distinction: RAG vs Decision Engine

The agent architecture maintains a clear separation between:

**Policy Retrieval (RAG):**
- Purpose: Identify which supplied policies are relevant
- Answers: "Which company policies apply?"
- Does NOT make authorization decisions

**Policy Enforcement (Decision Engine):**
- Purpose: Apply deterministic logic based on policy content
- Answers: "Given the evidence, what should the system do?"
- Interprets policy content and enforces rules
- Makes routing and escalation decisions

**LLM Role:**
- Natural language understanding and generation
- Does NOT independently invent or override policy

**Key Principle:** "RAG retrieves evidence; the policy engine enforces decisions."

This separation ensures:
- LLM handles language, not business logic
- Policies are enforced deterministically
- Decisions are explainable and traceable
- No uncontrolled AI decision-making

### Architectural Decision: Policy Granularity

Each supplied policy is treated as one retrieval document because the policy corpus is small (11 policies) and each policy is self-contained. Additional chunking would add complexity without improving retrieval for this dataset.

**Rationale:**
- Corpus is small and manageable
- Each policy addresses a specific topic
- Policies are already concise (2-3 sentences)
- No internal structure requiring segmentation

This decision may be revisited if the corpus grows significantly.

### Architectural Decision: Distance to Relevance Conversion

ChromaDB returns L2 distance (lower = more similar). We convert to relevance score using exponential decay: `relevance = e^(-distance)`

- Distance 0 → relevance 1.0 (highly relevant)
- Distance increases → relevance → 0 (less relevant)

**Important:** This score is a retrieval signal only, NOT authorization confidence or decision confidence.

### Separation of Concerns

**RAG retrieves relevant policy evidence.**

RAG does NOT:
- Make RESOLVE/FOLLOW_UP/ESCALATE decisions
- Authorize requests or approve actions
- Enforce policy rules or business logic
- Interpret policy content
- Create tickets

The decision engine (next phase) will interpret retrieved policies and make routing decisions.

### Structured Output Approach

Gemini's native structured output eliminates manual JSON parsing:

```python
response = client.models.generate_content(
    model=model_name,
    contents=prompt,
    config=types.GenerateContentConfig(
        response_mime_type="application/json",
        response_schema=ExtractedFacts,
    )
)
```

**Benefits:**
- Guaranteed schema conformance
- Type-safe throughout pipeline
- Pydantic validation built-in
- No regex or manual parsing

Use `unknown` for vague requests.

## Phase 6 — Agent Orchestrator

**Date:** 18 September 2026

### Objective

Build the thin orchestration layer that connects all agent components (request understanding → policy retrieval → ticket search → decision engine → response generation) into an end-to-end workflow.

### Completed

1. **Ticket Search Module** (`app/agent/ticket_search.py`)
   - Searches `data/tickets.json` based on intent and entities

2. **Response Generator** (`app/agent/response_generator.py`)
   - Uses Gemini to generate natural language message text
   - **CRITICAL:** Preserves decision from AgentDecision (CANNOT change it)
   - Falls back to deterministic message if LLM fails
   - Returns `AgentResponse` with message + preserved decision

3. **Orchestrator** (`app/agent/orchestrator.py`)
   - Thin coordination layer with NO business logic
   - Connects 5 components: understand_request → retrieve_policies → search_tickets → evaluate_decision → generate_response
   - Implements graceful degradation: RAG/ticket failures → empty lists, continue workflow
   - Implements hard failures: LLM understanding/decision engine → raise ValueError, stop workflow

4. **Tests** (`tests/test_phase6_orchestrator.py`)
   - 6 test scenarios covering happy path, error handling, decision preservation
   - All tests use mocks - NO real API keys required
   - Total project tests: 108 passing

5. **Documentation** (`docs/08-orchestrator.md`)
   - Architecture diagram showing 5-step workflow
   - Component responsibilities and failure modes
   - Decision preservation explanation (why Decision Engine is authoritative)
   - Error handling strategy (hard vs soft failures)
   - Usage examples and limitations

### Key Architectural Decisions

1. **Decision Engine Is Authoritative**
   - Decision Engine makes business decision (RESOLVE/FOLLOW_UP/ESCALATE)
   - Response Generator ONLY generates message text
   - Final AgentResponse preserves decision value unchanged
   - Prevents LLM from overriding policy enforcement

2. **Graceful Degradation**
   - RAG failure → empty policy list → decision engine handles
   - Ticket search failure → empty ticket list → decision engine handles
   - Response generator failure → deterministic fallback message

3. **No Side Effects**
   - Phase 6 is read-only: retrieves policies, searches tickets
   - Does NOT: create tickets, update tickets, modify policies, send emails
   - Side effects deferred to future phases or outside agent scope

4. **Thin Coordination Only**
   - Orchestrator contains NO business logic
   - All policy rules in `app/agent/policy_rules.py`
   - All decision logic in `app/agent/decision_engine.py`
   - Orchestrator only calls components in sequence and handles errors
