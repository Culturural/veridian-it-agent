# Data Contracts

## Overview

The Veridian IT Service Agent uses strongly typed Pydantic models to enforce data contracts throughout the application. These models are organized into three categories that must remain separate:

1. **Source Models** - Data directly from the Data Pack
2. **Derived Agent Models** - Information extracted by the agent
3. **System Models** - Information generated by the application

This separation ensures data integrity, prevents policy invention, and maintains clear traceability.

## Source Models

Source models represent data directly supplied by the Veridian Corp Data Pack. These models are **immutable** and should not be modified or augmented with unsupported information.

### Policy

Represents a policy from the knowledge base or policy extracts.

**Location:** `app/database/models.py`

**Fields:**
- `id: str` - Policy ID (e.g., KB-01, ASSET-01)
- `title: str` - Policy title
- `category: str` - Policy category
- `content: str` - Full policy text as supplied
- `source_type: str` - Type: "knowledge_base" or "policy_extract"

**Constraints:**
- Frozen (immutable)
- All fields required
- Content must be preserved exactly as supplied

**Example:**
```python
Policy(
    id="KB-01",
    title="Password Reset",
    category="authentication",
    content="Employees can reset their own password via the self-service portal...",
    source_type="knowledge_base"
)
```

### EmployeeRequest

Represents an employee IT support request.

**Location:** `app/database/models.py`

**Fields:**
- `request_id: str` - Request ID (e.g., REQ-01)
- `employee: str` - Employee name
- `email: str` - Employee email address
- `date_opened: str` - Date request was opened
- `request: str` - Full request text as supplied
- `initial_action_taken: str` - Initial action status

**Constraints:**
- Frozen (immutable)
- All fields required
- Does NOT include: department, employee_type, priority, severity

**Example:**
```python
EmployeeRequest(
    request_id="REQ-01",
    employee="Aditi Sharma",
    email="aditi.sharma@veridian-corp.example",
    date_opened="Mon 21 Sep",
    request="My laptop won't turn on...",
    initial_action_taken="Not started"
)
```

### Ticket

Represents an existing ticket from the ticket queue.

**Location:** `app/database/models.py`

**Fields:**
- `ticket_id: str` - Ticket ID (e.g., TK-1042)
- `employee: str` - Employee name
- `issue_summary: str` - Brief issue description
- `status: str` - Ticket status as supplied

**Constraints:**
- Frozen (immutable)
- All fields required
- Status preserved exactly as supplied

**Example:**
```python
Ticket(
    ticket_id="TK-1042",
    employee="R. Verma",
    issue_summary="VPN credential expired",
    status="Resolved (closed)"
)
```

## Derived Agent Models

Derived models represent information extracted or interpreted by the agent from source data. This information is **not authoritative** and should not be treated as business fact.

### ExtractedFacts

Information derived from natural-language input through LLM analysis.

**Location:** `app/agent/schemas.py`

**Fields:**
- `intent: str` - Classified intent of the request
- `entities: Dict[str, Any]` - Extracted entities as key-value pairs
- `missing_information: List[str]` - Information needed but not present

**Characteristics:**
- Flexible entity structure allows unknown information to remain unknown
- Does not hard-code employee attributes
- Represents LLM interpretation, not source truth

**Example:**
```python
ExtractedFacts(
    intent="laptop_issue",
    entities={
        "device": "laptop",
        "age_years": 3.5
    },
    missing_information=[]
)
```

### PolicyEvidence

Retrieved policy evidence from the knowledge base.

**Location:** `app/agent/schemas.py`

**Fields:**
- `policy_id: str` - Policy ID from source
- `title: str` - Policy title
- `content: str` - Policy content as supplied
- `relevance: Optional[float]` - Optional relevance score (0.0-1.0)

**Constraints:**
- Content preserved from source (not modified)
- Relevance score validated between 0.0 and 1.0

**Example:**
```python
PolicyEvidence(
    policy_id="KB-01",
    title="Password Reset",
    content="Employees can reset their own password...",
    relevance=0.95
)
```

### TicketContext

Ticket information with derived active/closed status.

**Location:** `app/agent/schemas.py`

**Fields:**
- `ticket_id: str` - Ticket ID from source
- `employee: str` - Employee name
- `issue_summary: str` - Issue description
- `status: str` - Original status as supplied
- `is_active: bool` - Whether ticket is active (derived)

**Ticket Semantics:**
- **Closed (is_active=False):** Status contains "Resolved (closed)", "Rejected ... (closed)", or "Approved ... (closed)"
- **Active (is_active=True):** All other statuses

**Example:**
```python
# From closed ticket
TicketContext.from_ticket(ticket)  # is_active=False

# From active ticket
ticket = Ticket(ticket_id="TK-1043", status="Pending Security review (active)", ...)
context = TicketContext.from_ticket(ticket)  # is_active=True
```

## Decision Model

### AgentDecision

Structured decision made by the agent, combining extracted facts, retrieved evidence, and decision logic.

**Location:** `app/agent/schemas.py`

**Fields:**
- `decision: Literal["RESOLVE", "FOLLOW_UP", "ESCALATE"]` - Agent decision type
- `intent: str` - Classified intent
- `confidence: float` - Confidence score (0.0-1.0)
- `extracted_facts: ExtractedFacts` - Facts extracted from request
- `relevant_policies: List[PolicyEvidence]` - Retrieved policies
- `relevant_tickets: List[TicketContext]` - Historical/active tickets
- `missing_information: List[str]` - Information needed to proceed
- `reason: str` - Explanation for the decision
- `actions: List[str]` - Recommended actions
- `sources: List[str]` - Policy IDs or source references

**Decision Types:**
- **RESOLVE** - Agent can handle the request
- **FOLLOW_UP** - More information needed
- **ESCALATE** - Request is risky, unclear, or requires human review

**Validation:**
- Confidence must be between 0.0 and 1.0
- Decision must be one of the three literal types

**Example:**
```python
AgentDecision(
    decision="RESOLVE",
    intent="password_reset",
    confidence=0.95,
    extracted_facts=facts,
    relevant_policies=[evidence],
    relevant_tickets=[],
    missing_information=[],
    reason="Employee is locked out after failed login attempts.",
    actions=["Unlock account manually"],
    sources=["KB-01"]
)
```

## User Response Model

### AgentResponse

User-facing response from the agent - concise, clear, and actionable.

**Location:** `app/agent/schemas.py`

**Fields:**
- `message: str` - User-facing response message
- `decision: Literal["RESOLVE", "FOLLOW_UP", "ESCALATE"]` - Decision type
- `sources: List[str]` - Policy IDs or sources cited
- `ticket_id: Optional[str]` - Generated ticket ID if created
- `follow_up_questions: List[str]` - Questions if more info needed

**Characteristics:**
- Does NOT contain internal reasoning or chain-of-thought
- Contains only concise, user-facing justification
- Cites sources for transparency

**Example:**
```python
AgentResponse(
    message="I can help you reset your password. You can use the self-service portal...",
    decision="RESOLVE",
    sources=["KB-01"],
    ticket_id=None,
    follow_up_questions=[]
)
```

## System Model

### AuditEvent

System-generated audit event for tracking and compliance.

**Location:** `app/database/models.py`

**Fields:**
- `event_type: str` - Type of audit event
- `timestamp: str` - ISO timestamp of the event
- `request_id: Optional[str]` - Associated request ID if applicable
- `details: dict` - Additional event details

**Characteristics:**
- System-generated (not from source data)
- Used for audit trail and compliance
- Flexible details field for event-specific information

**Example:**
```python
AuditEvent(
    event_type="request_processed",
    timestamp="2026-09-18T10:30:00Z",
    request_id="REQ-01",
    details={"decision": "RESOLVE", "confidence": 0.95}
)
```

## Agent Architecture: RAG vs Decision Engine

### Critical Distinction

The agent architecture separates **policy retrieval** from **policy enforcement**:

#### 1. Policy Retrieval / RAG

**Purpose:** Identify which supplied policies are relevant to the user's request.

**RAG answers:** "Which company policies are relevant?"

**What it does:**
- Semantic search over policy documents
- Retrieves potentially relevant policy evidence
- Assigns relevance scores

**What it does NOT do:**
- Make decisions about whether actions are permitted
- Enforce approval workflows
- Apply business logic
- Override or invent policies

#### 2. Policy Enforcement / Decision Engine

**Purpose:** Apply deterministic logic based on supplied policy content, extracted facts, required information, and relevant ticket context.

**Decision Engine answers:** "Given the relevant evidence and available facts, what should the system do?"

**What it does:**
- Interprets policy content
- Applies approval requirements
- Enforces limits and thresholds
- Determines escalation conditions
- Makes routing decisions based on rules
- Validates required information is present

**What it does NOT do:**
- Rely solely on LLM interpretation
- Make uncontrolled business decisions
- Invent policies or workflows

#### 3. LLM

**Purpose:** Natural-language understanding, extraction, clarification, and response generation.

**What it does:**
- Parse natural language requests
- Extract intent and entities
- Identify missing information
- Generate follow-up questions
- Create user-facing responses

**What it does NOT do:**
- Independently invent company policy
- Override deterministic business rules
- Make final authorization decisions

### Key Principle

**"RAG retrieves evidence; the policy engine enforces decisions."**

The LLM helps understand what the user wants. RAG finds relevant policies. The decision engine applies those policies deterministically.

### Conceptual Data Flow

```
User Request (natural language)
    ↓
LLM / Classifier
    ↓
ExtractedFacts (intent, entities, missing info)
    ↓
Policy Retrieval (RAG)
    ↓
PolicyEvidence (relevant policies with scores)
    +
TicketContext (historical precedent)
    ↓
Deterministic Decision Engine
    ↓
AgentDecision (RESOLVE / FOLLOW_UP / ESCALATE)
    ↓
Response Generator (LLM)
    ↓
AgentResponse (user-facing message)
```

Each stage has clear responsibilities and boundaries enforced by Pydantic contracts.

## Source vs Derived vs System Data

### Why This Separation Matters

**Data Integrity:**
- Source data cannot be accidentally modified or corrupted
- Agent interpretations are clearly marked as derived
- System operations are tracked separately

**Prevents Policy Invention:**
- Source models are frozen and immutable
- No business facts can be added to source records
- Unsupported information cannot leak into authoritative data

**Traceability:**
- Every agent decision can be traced to source policies
- Derived facts are clearly distinguished from ground truth
- Audit events track system operations

**Validation:**
- Pydantic enforces structural integrity at every boundary
- Invalid data cannot flow through the system
- Type errors are caught early

### Data Flow

```
SOURCE DATA (immutable)
    ↓
AGENT ANALYSIS (derived facts)
    ↓
POLICY RETRIEVAL (evidence)
    ↓
DECISION ENGINE (decision + reasoning)
    ↓
RESPONSE GENERATION (user message)
    ↓
SYSTEM OPERATIONS (audit logs, tickets)
```

Each stage has clear input/output contracts enforced by Pydantic models.

## Validation

Pydantic validation provides multiple layers of protection:

### Structural Validation
- Required fields must be present
- Field types must match declared types
- Extra fields are rejected (by default)

### Value Validation
- Confidence scores constrained to 0.0-1.0
- Relevance scores constrained to 0.0-1.0
- Decision types limited to valid literals

### Custom Validation
- Ticket active/closed semantics enforced
- Field validators can enforce business rules
- Immutability prevents accidental modification

### Benefits

1. **Early Error Detection** - Invalid data is caught at construction time
2. **Type Safety** - IDEs and type checkers can verify correctness
3. **Documentation** - Models serve as executable documentation
4. **Serialization** - Easy conversion to/from JSON for storage and APIs
5. **Testing** - Clear contracts make testing straightforward

## Usage Guidelines

### DO:
- Load source data into immutable source models
- Use derived models for LLM outputs
- Cite source policies in decisions
- Validate confidence scores
- Track system operations in audit events

### DO NOT:
- Modify source model content
- Add unsupported fields to source models
- Treat derived facts as authoritative
- Skip validation for convenience
- Mix source and derived data in the same model

## Testing

All models are covered by unit tests in `tests/test_models.py` that verify:
- Valid model creation
- Field validation
- Constraint enforcement
- Ticket semantics
- Invalid input rejection

Tests do not require external services and run quickly in isolation.
