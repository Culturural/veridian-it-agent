# RAG Architecture

## 1. Purpose

The Veridian IT Service Agent uses Retrieval-Augmented Generation (RAG) to identify which supplied company policies are relevant to an employee's IT support request.

**RAG answers the question:** "Which company policies are relevant to this request?"

**RAG does NOT:**
- Make RESOLVE/FOLLOW_UP/ESCALATE decisions
- Authorize requests or approve actions
- Enforce policy rules or business logic
- Invent or modify policy content
- Create tickets or audit logs

The agent architecture maintains a clear separation:
- **RAG retrieves evidence**
- **The policy engine enforces decisions**

This separation ensures that:
1. Policy interpretation remains deterministic
2. Business logic is explainable and traceable
3. The LLM cannot override company policy
4. Retrieval is independent of authorization

## 2. Source

The authoritative policy source is:

```
data/policies.json
```

This file contains exactly **11 policies**:
- KB-01 through KB-10 (knowledge base articles)
- ASSET-01 (policy extract)

All policy content is preserved exactly as supplied. RAG does not modify, summarize, or rewrite policies.

## 3. Policy Granularity

**Each policy is treated as a single retrieval document.**

The supplied policy corpus consists of concise, self-contained policy records. Each policy (KB-01, KB-02, etc.) addresses a specific topic and is already appropriately scoped for retrieval.

**Rationale:**
- The corpus is small (11 policies)
- Each policy is self-contained
- Policies are already concise
- No policy requires internal chunking for comprehension
- Additional text chunking would add complexity without improving retrieval

**Example:**
```
KB-01 → 1 document (Password Reset)
KB-02 → 1 document (VPN Access)
KB-03 → 1 document (Laptop Replacement)
...
ASSET-01 → 1 document (Asset Management Policy)
```

This design decision may be revisited if the policy corpus grows significantly or if policies become substantially longer.

## 4. Embeddings

### Concept

Embeddings convert text into numerical vectors (arrays of numbers) that capture semantic meaning. Similar text produces similar vectors.

**How it works:**
1. Policy text (natural language) → Embedding model → Vector (e.g., 1536 dimensions)
2. Query text (user request) → Same embedding model → Query vector
3. Compare vectors using mathematical similarity (e.g., cosine similarity, L2 distance)
4. Most similar vectors = most relevant policies

### Implementation

We use **OpenAI's embedding API** to generate embeddings:
- Default model: `text-embedding-3-small`
- Configurable via `OPENAI_EMBEDDING_MODEL` environment variable
- Same model must be used for both policy ingestion and query embedding

**Why OpenAI embeddings:**
- High-quality semantic understanding
- Consistent and reliable
- Well-tested at scale
- Same provider as the LLM (OpenAI API)

### Configuration

Embedding model can be configured via environment variable:
```bash
OPENAI_EMBEDDING_MODEL=text-embedding-3-small
```

If not set, defaults to `text-embedding-3-small`.

## 5. ChromaDB

### Role

ChromaDB is the persistent vector database that stores policy embeddings and enables semantic search.

**What ChromaDB does:**
- Stores policy text and embeddings
- Stores policy metadata (ID, title, category, source type)
- Performs efficient similarity search
- Returns the most relevant policies for a query

**Storage location:**
```
data/chroma/
```

### Collection Structure

**Collection name:** `veridian_policies`

Each document in the collection contains:

**ID:** Exact policy ID (e.g., `KB-02`)

**Document:** Exact policy content (preserved from source)

**Metadata:**
```json
{
  "policy_id": "KB-02",
  "title": "VPN Access",
  "category": "vpn",
  "source_type": "knowledge_base"
}
```

**Embedding:** Generated by OpenAI (stored internally by ChromaDB)

### Persistence

ChromaDB uses persistent storage, so:
- Policies remain stored after the application exits
- Ingestion is idempotent (safe to run multiple times)
- No re-ingestion needed unless policies change

## 6. Retrieval

### Semantic Similarity Search

When a user submits a request:

1. **Query embedding:** User's request text is converted to a vector using the same embedding model
2. **Similarity search:** ChromaDB compares the query vector to all policy vectors
3. **Ranking:** Policies are ranked by similarity (lower distance = more similar)
4. **Top-K selection:** The top K most similar policies are returned

**Example:**
```
User request: "My VPN stopped working this morning"

Retrieval:
1. KB-02 (VPN Access) - distance: 0.15 → highly relevant
2. KB-07 (Guest Wi-Fi Access) - distance: 0.45 → somewhat relevant
3. KB-01 (Password Reset) - distance: 0.68 → less relevant
```

### Parameters

**`query: str`** - The user's request text (must be non-empty)

**`top_k: int`** - Number of policies to retrieve (default: 3, must be positive)

### Distance to Relevance Conversion

ChromaDB returns **L2 (Euclidean) distance** by default:
- Lower distance = more similar
- Distance of 0 = identical
- Distance increases as similarity decreases

We convert distance to a **relevance score** (0.0 to 1.0) using exponential decay:

```
relevance = e^(-distance)
```

**Where:**
- Distance ≈ 0 → relevance ≈ 1.0 (highly relevant)
- Distance increases → relevance → 0.0 (less relevant)

### Important: Relevance Score Interpretation

The relevance score is **a retrieval signal only**. It indicates how semantically similar the policy is to the query.

**The score is NOT:**
- Probability that the policy is correct
- LLM confidence in the answer
- Authorization confidence
- A decision about whether to approve the request

The **decision engine** (not RAG) determines what action to take based on the retrieved policy content.

## 7. PolicyEvidence

### Data Flow

Retrieval results are converted into `PolicyEvidence` objects before entering the agent pipeline:

```python
class PolicyEvidence(BaseModel):
    policy_id: str        # e.g., "KB-02"
    title: str            # e.g., "VPN Access"
    content: str          # Exact policy text
    relevance: float      # 0.0 to 1.0
```

**Why PolicyEvidence:**
- Provides a clean contract between RAG and the decision engine
- Preserves policy ID for traceability
- Preserves exact policy content (not summarized)
- Includes relevance as a ranking signal
- Type-safe using Pydantic validation

### Example Flow

```
User Request: "My VPN stopped working"
    ↓
RAG Retrieval
    ↓
[
  PolicyEvidence(
    policy_id="KB-02",
    title="VPN Access",
    content="VPN access is granted automatically...",
    relevance=0.86
  )
]
    ↓
Decision Engine (later phase)
```

## 8. Retrieval vs Enforcement

**Critical Distinction:**

### RAG (This Phase)
**Role:** Retrieve relevant policy evidence

**Answers:** "Which policies apply?"

**Does:**
- Load policies from source
- Generate embeddings
- Store in vector database
- Perform semantic search
- Return PolicyEvidence objects

**Does NOT:**
- Interpret policy content
- Make authorization decisions
- Enforce approval requirements
- Apply business rules
- Determine escalation conditions

### Policy Engine (Future Phase)
**Role:** Enforce policy and make decisions

**Answers:** "What should the system do?"

**Does:**
- Interpret policy content
- Apply approval workflows
- Enforce limits and thresholds
- Determine RESOLVE/FOLLOW_UP/ESCALATE
- Route requests appropriately

**Does NOT:**
- Search for policies (uses RAG output)
- Generate embeddings
- Perform semantic search

### Key Principle

**"RAG retrieves evidence; the policy engine enforces decisions."**

This separation ensures:
1. **Explainability** - Every decision traces to specific policies
2. **Determinism** - Business logic is rule-based, not LLM-dependent
3. **Traceability** - Policy sources are explicitly cited
4. **Control** - LLM cannot override company policy

## 9. Limitations

### Retrieval Limitations

**1. Semantic Similarity ≠ Policy Applicability**

A policy may be semantically similar but not actually applicable:
- Query: "I need a new laptop"
- Retrieved: KB-03 (Laptop Replacement)
- But: Policy requires 3 years of service or hardware failure
- Decision engine must check requirements

**2. Relevance Score ≠ Approval Probability**

A high relevance score means the policy is semantically similar to the query. It does NOT mean:
- The request will be approved
- The policy permits the action
- The user is authorized

**3. Missing Context**

RAG retrieves policies based on query text alone. It does not consider:
- Employee attributes (not in source data)
- Previous ticket history (separate retrieval)
- Current state or timing
- Business context

The decision engine combines retrieval results with other context.

**4. Corpus Size**

With only 11 policies, retrieval may return moderately relevant results even for unclear requests. The decision engine must validate applicability.

**5. Query Quality**

Poor or ambiguous queries may retrieve less relevant policies:
- Query: "hey can you help, its not working"
- Challenge: No device, issue, or context specified
- Solution: Follow-up questions (handled by decision engine)

### Design Limitations

**6. No Cross-Policy Reasoning**

RAG retrieves individual policies. It does not:
- Combine information from multiple policies
- Resolve conflicts between policies
- Infer unstated rules

The decision engine handles policy interpretation.

**7. No Real-Time Updates**

Policies are ingested once. Changes to `data/policies.json` require re-running the ingestion script.

**8. Single Language**

Embeddings work best within a single language. Cross-language retrieval is not supported.

## Summary

The RAG system provides efficient, reliable policy retrieval to support the IT service agent. By maintaining clear separation between retrieval and enforcement, the system ensures explainable, traceable, and policy-compliant decision-making.
